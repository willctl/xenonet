# XenoNet 0.6.0

You can start a session on any machine in your network from this one, and a message that reaches a machine now goes straight into its session instead of waiting for that session's next turn. Sessions and actors can message each other in any pair, across machines. Windows gets a round of fixes from running XenoNet on a second PC. Desktop, Tools and the Service are 0.6.0.

## Start a session on another machine

- **Choose "Start a session…" on a machine:** its row in the Network panel, its card in Machines, or its node on the map. Pick a folder from that machine's projects, the app (Claude Code, Codex or Grok Build), a permission mode and the first prompt. The session starts there and shows on the map in a few seconds.
- **From a terminal:** `xenonet start --on <machine> --in <folder> "<prompt>"`. As you, this works from XenoNet's window or a terminal on a Mac, where XenoNet can check it's you.
- **From an agent:** sessions can use the `start_session` tool. The new session's first prompt says who asked for it.
- **Each machine decides who may start sessions on it:** nobody, you only (the default), or the network (you, and the sessions on machines where you use a XenoNet window). Set it in the machine's Network panel or with `xenonet net set --start`. From another machine you can always narrow it. Opening it to the network from elsewhere takes the network's founder or two window hosts.
- Starts come only from machines where you use a XenoNet window. A server you reach only in a terminal can have sessions started on it, but it can't start them anywhere.

## Messages arrive at once

- **With `xenonet net set --wake network`,** a message to a Claude Code, Codex or Grok Build session that isn't running starts one turn of it right away, with the message as its prompt. When the session is open in an app, a copy with its whole history answers instead, linked to it on the map. The usual wake limits apply.
- **Permission prompts come to you.** When a session XenoNet started or woke needs a permission, Needs you shows it on every machine where you use a XenoNet window, with Allow and Deny. Nobody answering in 10 minutes means deny.
- **Unattended runs need Claude Code signed in.** Run `xenonet runs sign-in` once on each machine and paste a token from `claude setup-token`, which you can make on any machine. XenoNet keeps it in the system's credential store and gives it only to the sessions it starts. Those sessions, and anyone who can prompt them, can read it. A call that would read it gets a warning on its Allow card. A run that fails because Claude Code isn't signed in says so.
- A paused XenoNet starts and wakes nothing, and the usual message limits apply to starts too.

## Messages between any pair

- An actor on one machine can message an actor on another.
- A message to an actor that can't read messages is refused at once, with the reason, instead of waiting forever.
- `send` says a message waits for a machine only when that machine is offline.
- A message another machine kept but nobody read for a week shows as unread.
- The Network panel counts this machine's own agents.

## Windows

- XenoNet finds the Claude Code that Claude desktop installs, so it can resume and start sessions on a machine with only Claude desktop.
- `xenonet service stop` holds, even when the service from your login was waiting to start.
- Updating the Tools works while agents are using them.
- `xenonet update` with no component lists what would change and asks first, and installs the Tools before the Service.
- XenoNet refuses what's yours to do (connecting your agents, installing the background service, joining a network) when it's run from under an agent, on Windows and Linux as well as macOS.
- The doctor checks Windows Defender Firewall on a network's gateway and gives the exact command to allow it.
- An uninstalled Codex shows as not installed in the doctor, not as a failure.
- The service runs git far less often: about 5 times a minute instead of 72 with a dozen repos.

## The actor gateway

- Tailscale Funnel now publishes only the gateway's `/mcp`. The network's own routes stay on your tailnet or LAN. A Funnel set up by an earlier version is narrowed the next time XenoNet checks it.
- Grok Bot's connect message no longer carries the gateway token: Grok Bot asks for it through its secret card, and **Copy token** copies it without showing it.

## Updating

1. Update Desktop. On Windows, open **Updates** and choose **Restart and update**. On a Mac, replace XenoNet in Applications with the copy from the new disk image, and open it.
2. Update the Tools, then the Service: in **Updates**, or with `xenonet update tools` and then `xenonet update service`.
3. To start sessions on a machine from another, or have messages arrive at once, set who may start and wake sessions there: in its Network panel, or on that machine with `xenonet net set --start network --wake network`. From another machine's window you can narrow these; opening them to the network from elsewhere takes the founder. Then run `xenonet runs sign-in` on it.

Update every machine in a network. A machine on 0.5.x can't take starts, and says so.

`SHA256SUMS.txt` lists checksums for the downloads.
