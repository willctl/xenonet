# XenoNet 0.4.0

XenoNet, the network for SI on your machine, now runs on one binary, `xenonet`: the service, the command, the hooks and the MCP servers. The Service and Tools packages carry no Node. This release also lets the service start at login on macOS, Linux and Windows, adds a plugin for Claude Code, reads Grok Build's sessions beside Claude Code's and Codex's, and adds a plain-panels setting that lowers the console's GPU use. Service and Tools are both 0.4.0.

After you update, connect your agents again. [Updating](#updating) says what to do.

## One binary, no Node

- Desktop starts the service as `xenonet serve`. Claude Code and Codex run `xenonet hook <app>` for their hooks and `xenonet mcp` for XenoNet's tools, instead of Node and a script.
- A hook takes about 3 ms from start to exit on a recent Mac, where one run through Node took about 88 ms. Codex runs two hooks for each tool call.
- The Service package for an Apple silicon Mac is about 12 MB to download, down from 161 MB, and the Tools about 11 MB, down from 160 MB. Each holds `bin/xenonet` and the schemas it reads the apps' data against, and the Service adds the console page it serves.
- Claude Code's sessions are read from its transcript files, the way the Agent SDK reads them, so nothing needs Node.
- On a made-up history of 3,000 sessions and 2 GB of transcripts, the service is ready in about half a second, builds its search index in about 11 seconds, opens the longest transcript (240 MB) in about half a second, and uses about 6% of a core while idle.
- If the Service's binary is missing, Desktop says so and asks you to reinstall XenoNet with the bundle installer. There's no other service for it to fall back to.

## The service at login

XenoNet's service can start when you log in, and start again if it stops unexpectedly. Then sessions keep messaging each other, claiming files and hearing about edit collisions while Desktop is closed. It's off until you turn it on.

- Installed Desktop asks once: "Keep XenoNet running in the background?" After that, **Background service** in the palette, the tray menu or the XenoNet menu on a Mac has the switch. From a terminal, `xenonet service install` turns it on, `xenonet service uninstall` turns it off, and `xenonet service status` says how it stands.
- On macOS it's a launch agent, on Linux a systemd user unit, and on Windows a scheduled task, **XenoNet Service**, that runs as you and needs no administrator.
- launchd starts a crashed service again at most every 10 seconds. On Linux and Windows it starts again 5 seconds after a failure, up to 10 times in 5 minutes. After `xenonet service stop`, it stays stopped until you next log in.
- Turning it on or off is yours to do. XenoNet refuses it from under an agent such as Claude Code or Codex.
- The doctor checks the registration under **Background service**, and `xenonet doctor --only service` runs that check alone.
- Uninstalling Desktop turns it off.

It starts at login, not at boot. On Linux, `loginctl enable-linger $USER` starts it at boot. On Windows, the scheduled task runs only while you're signed in. The menu bar icon, the tray and notifications still come from Desktop. If you change a XenoNet setting such as `XENONET_PORT` or `XENONET_GATEWAY_PORT` after turning it on, run `xenonet service install` again. [Keeping the service running](https://github.com/willctl/xenonet/blob/main/docs/guide/always-on.md) has the details.

## XenoNet's plugin for Claude Code

Claude Code can get XenoNet's MCP server and hooks from a plugin, instead of `Connect your agents to XenoNet`. Install XenoNet first, since the plugin runs the `xenonet` command from your PATH. Then, in Claude Code:

```text
/plugin marketplace add willctl/xenonet
/plugin install xenonet@xenonet
```

- The plugin adds the hooks connecting adds, the `xenonet` MCP server, and a skill, `xenonet:coordinate`, on working beside other sessions. In a session, its tools are named `mcp__plugin_xenonet_xenonet__peers` and so on.
- XenoNet keeps one copy of each hook. While the plugin is on, connecting Claude Code adds nothing and offers to take out connect's own entries. `xenonet doctor` warns when both are there.
- The plugin reaches the installed XenoNet on port 47840. Codex has no plugin, so connect it as before. On Windows, connect Claude Code from the palette or with `xenonet connect` instead.

[Sessions working together](https://github.com/willctl/xenonet/blob/main/docs/guide/agents.md#as-a-claude-code-plugin) has the details.

## Grok Build

XenoNet reads the sessions of Grok Build, the `grok` command, as it reads Claude Code's and Codex's. They're on the map in a color of their own in every theme, and in the live tailer, stats, search and the doctor. Once you connect Grok Build, its sessions can see and message the others.

- `Connect your agents to XenoNet` lists Grok Build once it's installed, and `xenonet connect grok` connects it alone. XenoNet adds its `[mcp_servers.xenonet]` tables to `~/.grok/config.toml`, leaves every other line as it was, comments included, and keeps a copy as `config.toml.before-xenonet` the first time. Its hooks go in a file of their own, `~/.grok/hooks/xenonet.json`. `GROK_HOME` moves both.
- Grok Build runs the hooks in `~/.grok/hooks` without asking. An organization's `allow_managed_hooks_only`, or XenoNet's hooks turned off in `/hooks`, stop them, and the doctor says so.
- On macOS, a request in a Grok Build session's name must come from a `grok` process or from under one.

Grok Build reads a hook's answer only at some events. So a Grok Build session doesn't hear who else works in its repo when it starts (its `peers` tool says), an edit warning arrives with the edit's result, and messages arrive with tool results and at the end of a turn. Its sessions show no tokens or cost yet, can't be renamed or opened in an app, and show the first chunk of each streamed reply. Questions it asks you and its edit collisions aren't read from its updates yet. XenoNet reads Grok Build's files as Grok Build 1.0.50's source writes them, and its tests use made-up sessions in those shapes. [Grok Build in XenoNet](https://github.com/willctl/xenonet/blob/main/docs/design/grok-build.md) has the details.

## Codex

- Archived Codex threads (`.jsonl.zst`) keep their stats, search results and transcripts. The binary reads the archives as the JS service did, and refuses one that would decompress to more than 1 GiB.
- Live counts a Codex session's output as OpenAI's `output_tokens` alone, as XenoNet's prices do. It used to add the reasoning tokens on top, though OpenAI counts them inside `output_tokens`, so a session's live output was larger than what it was priced for.
- Live counts the files an `apply_patch` moves to. A moved file shows as the session's activity, and counts when two sessions work on one file.
- **Summarize with Codex**, and asking Codex which folders are projects, run `codex exec` in a Codex home of its own that links your `auth.json` and nothing else. Your plugins, hooks, MCP servers and `AGENTS.md` stay out of those runs, and their shell and web search are off. If your Codex keeps its sign-in in the keychain rather than in `auth.json`, these runs say Codex isn't signed in.

## Xenolith

The page and the demo call the shared context Xenolith, and XenoNet reads the wiki as Xenolith writes it.

- Xenolith's spaces, a wiki for each project, identity, actor or machine in `spaces/<kind>/<name>/`, show in the constellation, and a project space's pages tie to that project. A write to a space beams to that space's pages.
- Links written `[[slug|text]]` count. A page without a `title` takes its first top-level heading. Types are read in lowercase, and the palette finds a page by its `aliases`.
- XenoNet finds the wiki where Xenolith does: `XENOLITH_DIR`, then `wikiDir` in Xenolith's `config.json`, then `~/Xenolith`. `XENONET_WIKI_DIR` still overrides it.
- Pages, logs and notes that are links to files elsewhere are left out, as Xenolith leaves them out.

Xenolith itself still installs on its own, from `xenolith/` in this repository. See [Shared context](https://github.com/willctl/xenonet/blob/main/docs/guide/shared-context.md).

## Plain panels and a lighter map

- `Turn plain panels on or off` in the palette draws the panels solid, without the glass blur of the map behind them. On the demo, on an M3 Max, a frame took about 40% less GPU time with it, at the median. It's off by default, and the window remembers it.
- Each frame of the map costs less and looks the same: about a fifth fewer draw calls, and about 230 MB less GPU memory.

## Refusals

- When a command or a route names an app whose transcripts XenoNet doesn't read, XenoNet refuses it and names the app, instead of taking it for Claude Code or Codex. `xenonet hook gemini-cli` used to post to Codex's hook, and a handoff to an unknown app went to Claude Code. Now a route answers 400, `xenonet diagnose --ask --app` gives a usage error, and `xenonet hook` drops the event with a line in XenoNet's log, still exiting 0 so the agent carries on. Leaving the app out still takes the default.
- A request in the name of a session of an app whose processes XenoNet can't tell apart, such as a Gemini CLI, Copilot CLI or Cursor session, is refused on every system, hooks included. It used to go through unchecked. Those sessions still show on the map. Claude Code, Codex, Grok Build and OpenCode are the apps XenoNet checks. Actors call with their tokens, so this doesn't change them.
- The binary's readers of other programs' files, hook payloads and requests were fuzzed for about 13.5 hours across 16 targets, and what turned up is fixed.

## The actor gateway's port

The actor gateway listened on XenoNet's port plus 10, which is 47850 for an installed XenoNet. That's Xenolith's port, so whichever started second couldn't listen. The default is now XenoNet's port plus 1010, which is 48850.

- A gateway you already set up (turned on, or given a tunnel or a public address) keeps its port. XenoNet saves the port with the gateway's settings the first time 0.4.0 starts, so its tunnel and the apps that use it keep working.
- A gateway never set up takes 48850. `XENONET_GATEWAY_PORT` still names a port of your choosing.
- If a tunnel of your own forwards to the gateway, check that it points at the port `xenonet gateway` shows on this machine.
- To move a gateway off 47850, start XenoNet with `XENONET_GATEWAY_PORT` set to the port you want. XenoNet sets up the tunnels it runs again, and the window offers Repair for Tailscale Funnel. Point a tunnel of your own at the new port yourself.

## OpenCode ids

One reading of OpenCode's ids now serves the OpenCode reader, numbat and delivery. A run that both the reader and numbat record is one session, and a message reaches the session its id came from.

- An id of letters and digits joined by single underscores, as OpenCode writes them, reads as before: `ses_4f…` is `opencode:ses-4f…`.
- Any other id is `opencode:x--` and the id's bytes in hex, and reads back whole.

## Windows

- The service can start at sign-in through Task Scheduler. See [The service at login](#the-service-at-login).
- XenoNet runs the same `xenonet` binary on Windows. CI builds it and runs the Rust tests and the binary's tests on Windows, as on macOS and Linux.
- Uninstalling Desktop runs the launcher's `xenonet.exe` to turn off the scheduled task. When you remove your data too, it also disconnects your agents and stops the service.
- `xenonet diagnose` also looks for a Windows home folder in the JSON form of its summary, where backslashes are doubled, and refuses to make a summary that holds one.

The panel of this computer's load shows the GPU on Windows, but not yet the CPU's or memory's use. As before, XenoNet doesn't check which program sent a request on Windows. Connect Claude Code from the palette or with `xenonet connect`, rather than through the plugin.

## Updating

On Windows, open **Updates** and choose **Restart and update** for Desktop. Then install the Service and Tools updates there, or run `xenonet update all`.

On a Mac, replace XenoNet in Applications with the copy from the new disk image, and run `xenonet update all`. Your settings stay in place.

Without Desktop, `xenonet update all` is the whole update. The service update waits while XenoNet's terminals run, so close them first.

Then:

- Connect your agents again, with `Connect your agents to XenoNet` in the palette or `xenonet connect`. The hooks and MCP entries 0.3.0 added keep working. Connecting again replaces them with entries that run the `xenonet` binary, and until then the doctor reports Claude Code and Codex as partly connected. Sessions already running pick up the change when they restart. Connecting also adds Grok Build, if it's installed.
- If the doctor says the `xenonet` command runs something that's gone, choose `Install the xenonet command` in the palette.
- A gateway you set up keeps its port. See [The actor gateway's port](#the-actor-gateways-port).

`SHA256SUMS.txt` lists checksums for the downloads.
