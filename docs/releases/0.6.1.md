# XenoNet 0.6.1

Fixes for starting sessions on another machine, found while setting up a second PC on 0.6.0. Desktop, Tools and the Service are 0.6.1.

## Fixes

- **`xenonet runs sign-in` keeps the token.** In 0.6.0 it failed on every system with "a credential's name is printable text, without quotes or backslashes", so the sessions XenoNet starts and wakes had no sign-in of their own.
- **XenoNet finds Claude Code where its installer puts it,** `~/.local/bin`, even when that folder isn't on PATH. On Windows the installer leaves it off PATH, so a machine with Claude Code installed said "claude isn't installed here".
- **Flags take a value after a space.** `xenonet net set --on <machine> --start network`, `xenonet start --on <machine> --in <folder>`, `logs --component`, `logs --code`, `diagnose --model`, `refusals --provider` and `live --hours` work as their help shows. In 0.6.0 only `--flag=value` did, and `net set --on <machine>` said "true isn't in the network".
- **`xenonet service stop` waits until the service has stopped,** so a `service start` right after starts a new one. With no service running, it says so.

## Updating

1. Update Desktop. On Windows, open **Updates** and choose **Restart and update**. On a Mac, replace XenoNet in Applications with the copy from the new disk image, and open it.
2. Update the Tools, then the Service: in **Updates**, or with `xenonet update tools` and then `xenonet update service`.
3. On a machine where sessions are started or woken for others, sign XenoNet's runs in again, since 0.6.0 couldn't keep the token: `claude setup-token`, then `xenonet runs sign-in`.

`SHA256SUMS.txt` lists checksums for the downloads.
